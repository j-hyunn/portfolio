## AI 모델 — Gemini

**선택 이유**
- Google ADK(에이전트 프레임워크)와 자연스럽게 통합됨
- Gemini 2.5 Flash는 한국어 품질이 우수하고, 서버 비용 대비 성능이 좋음
- Google AI Studio에서 무료 API 키 발급 가능 → 사용자도 자신의 키로 업그레이드 가능 (BYOK)

**선택하지 않은 대안**
- OpenAI / Claude: 성능은 유사하나 Google ADK와의 통합을 포기해야 하고, 면접관 에이전트 전체를 재설계해야 함. 수요 확인 후 v2에서 검토.

**작업별 모델 분리**
- 면접 / 평가 / 분석 / 이력서 생성 → `gemini-2.5-flash` (사용자 BYOK 시 `gemini-2.5-pro` / `gemini-3.1-pro-preview` 선택 가능)
- **문서 정제(normalize) → `gemini-2.5-flash-lite`로 분리** (항상 서버 키). 큰 포트폴리오(16K자+) 입력 시 flash는 응답 45초 이상 걸려 실패했음 → lite는 latency 1/2~1/3 수준이라 같은 입력도 ~20초 안에 응답. 정제는 텍스트 재구성 작업이라 lite 품질로 충분.
- 음성(TTS/STT) → 전용 모델 고정, 항상 서버 키

**알려진 제약 — 면접 대화만은 상위 모델이 적용되지 않는다**
사용자가 자기 키로 `gemini-3.1-pro-preview`를 선택해도 **면접 대화 자체는 기본 `gemini-2.5-flash`로 진행된다.** 면접관 에이전트가 프로그램 시작 시 서버 키로 한 번 만들어지고 재사용되는 구조여서, 사용자별 키가 끼어들 지점이 없다. 상위 모델은 질문 생성·힌트·평가·이력서 생성에만 적용된다. 의도한 동작인지 확인이 필요한 항목이다.

**선택 이유**

## 웹 프레임워크 — Next.js + Vercel

**선택 이유**
- 프론트엔드와 백엔드(API Route, Server Actions)를 하나의 코드베이스에서 관리
- Vercel에 원클릭 배포 + 무료 티어로 초기 비용 없음
- 서버사이드 렌더링으로 SEO 대응 가능

**해결한 문제**
- Vercel 무료 플랜의 파일 업로드 4.5MB 제한 → Presigned URL 방식으로 우회 (파일이 Vercel을 거치지 않고 Supabase로 직접 업로드됨)
- 업로드 응답이 30~60초 걸려 자주 실패 → Next.js `after()` 콜백으로 정제 작업을 백그라운드 분리, 응답은 ~5초 (2026-05-17 패치)

**미해결 — 함수 실행 시간 한도**
AI 라우트 두 개(`/api/interview`, `/api/resume/generate`)에 실행 시간 상한을 **300초**로 설정해 뒀다. 그런데 문서 전반은 "무료 티어 60초"를 전제로 쓰여 있다. 현재 플랜에서 300초가 실제로 허용되는지 확인이 필요하고, 허용되지 않는다면 이력서 4단계 생성과 평가 예산(240초) 설계를 다시 잡아야 한다.

## 이력서 저장 방식 — 테이블 2개로 분리 + JSONB (2026-07-26)

**왜 마스터 이력서와 제출용 이력서를 나눴는가**
- 두 데이터의 성격이 다르다. **마스터 이력서**는 계속 갱신하는 내 자산이고, **제출용 이력서**는 특정 회사에 낸 시점의 스냅샷이다.
- 한 곳에 섞어두면 "마스터를 수정했을 때 이미 제출한 이력서도 바뀌어야 하나?"라는 답 없는 문제가 생긴다. 분리하면 **제출 당시의 이력서가 그대로 보존**된다 — 면접 준비에는 이 쪽이 맞다.

**왜 섹션별로 테이블을 쪼개지 않고 JSONB 한 덩어리로 저장했는가**
- 경력·프로젝트·학력을 각각 테이블로 만들면 조회할 때마다 5~6개를 합쳐야 하는데, 실제 사용 패턴은 **항상 전체를 한 번에 읽고 한 번에 저장**하는 것이다. 부분 조회·부분 수정 요구가 없다.
- 스키마가 자주 바뀌는 초기 단계에서 변경 비용이 훨씬 낮다.
- **트레이드오프:** DB가 구조를 검증해주지 않는다. 실제로 이 때문에 AI가 만든 이력서의 요약문이 엉뚱한 위치에 저장되는 문제가 발생했고, 읽는 쪽에서 두 위치를 모두 확인하는 방식으로 임시 대응했다. 근본 해결은 저장 전 구조 검증 도입이다.

## 이력서 생성 — 4단계로 나눈 이유 (2026-07-26)

JD에 맞는 이력서를 만드는 작업을 AI 호출 한 번으로 끝내지 않고 네 단계로 나눴다.

```
1단계  채용공고 분석 → 이 포지션이 원하는 핵심 역량 3가지를 먼저 확정
2단계  마스터 이력서에서 그 역량에 맞는 경험만 골라내기 (문장은 그대로)
3단계  골라낸 경험의 문장만 제출용 형태로 다시 쓰기 (개조식·수치 포함)
4단계  결과를 분석해 키워드 매핑·강조 포인트·부족한 항목 도출
```

**왜 나눴는가**
- 한 번에 시키면 **"골라내기"와 "문장 고치기"가 섞여 선별 기준이 무너진다.** 두 지시를 동시에 주면 AI가 둘 다 어중간하게 한다.
- 1단계에서 기준(핵심 역량 3가지)을 **먼저 고정**해야 2·3단계가 같은 잣대로 판단한다. 매번 기준을 다시 추론하면 단계마다 다른 결론이 나온다.
- 단계가 분리돼 있으면 실패했을 때 "채용공고 분석 실패" / "문장 변환 실패"처럼 구체적으로 안내할 수 있다.

**트레이드오프**
- 호출 4번을 순서대로 하니 생성 1건에 수십 초 걸린다. 각 단계가 앞 단계 결과에 의존하므로 병렬화할 수 없다.
- AI 비용도 4배. 사용자 자기 키(BYOK) 유도나 생성 횟수 제한이 수익 모델 검토 대상이다.

## 이력서 에디터 — tiptap (2026-07-26)

**선택 이유**
- 이력서 본문은 불릿 목록이 기본 형태인데, 일반 텍스트 입력창에서는 사용자가 `-`를 직접 타이핑해야 하고 결과를 볼 수 없다.

**선택하지 않은 대안**
- 리치 텍스트 에디터(HTML 저장): 저장된 HTML 태그가 AI 프롬프트에 섞여 토큰을 낭비하고 AI가 오독한다.
- 일반 입력창 + 미리보기 분리: 구현은 간단하나 긴 이력서를 쓸 때 입력·확인 왕복이 번거롭다.

## PDF 파싱 라이브러리 — unpdf

**선택 이유**
- 처음엔 `pdf-parse` → `pdfjs-dist` 순으로 시도했으나 Vercel 서버 환경에서 호환성 오류 발생
- `unpdf`는 서버 환경을 고려해 설계된 라이브러리로 문제없이 동작

**결정 포인트**
- DOCX 지원은 처음엔 계획했으나 실제 이력서 대부분이 PDF → 불필요한 복잡도로 판단해 제거

**운영 함정 — lockfile sync (2026-05-17 발견)**
- `package.json`에는 라이브러리가 있지만 `package-lock.json`이 어긋나면 개발 환경에 실제 패키지가 누락된다
- 이 경우 **모든 PDF가 0자로 추출되어 모든 업로드가 실패**한다. Vercel 배포 환경은 정상 동작하므로 개발·운영 동작이 달라진다
- 해결: `npm install` 후 `package-lock.json` 커밋

**한계 — 텍스트는 있지만 추출 실패 케이스 (v2 검토)**
- 폰트가 이미지처럼 처리된 디자이너 포트폴리오 등은 0자로 추출된다
- 현재는 명시적 거부 처리 (파일 정리 + 에러 안내)
- v2: `pdfjs-dist` 직접 호출 fallback, 스캔본은 OCR 별도 처리

## Git 링크 — 기능 제거 (2026-07-26)

원래는 GitHub URL을 입력받아 README를 읽어 면접 컨텍스트로 쓰려 했으나 **기능 자체를 제거했다.**

**이유**
- 대부분의 README는 설치법·사용법이라 **지원자의 역할·판단·성과가 드러나지 않는다.** URL 한 줄이 면접 질문 품질에 기여하는 바가 거의 없었다
- 코드·커밋 분석까지 하면 의미가 있겠지만 비용이 크고, 그 없이는 값이 사실상 0이었다
- 마스터 이력서의 프로젝트 섹션이 그 역할을 훨씬 정확하게 대체한다 — 사용자가 직접 "무엇을 했고 어떤 성과를 냈는지" 구조화해 입력하기 때문

## 사용자 API 키 보안 — AES-256-GCM 암호화

**선택 이유**
- 사용자가 자신의 Gemini API 키를 등록하면 DB에 저장되는데, 평문으로 두면 DB가 탈취될 때 키 전체가 노출
- AES-256-GCM으로 암호화하면 암호화 키(`ENCRYPTION_KEY`)가 없으면 복호화 불가
- 복호화는 서버에서만 수행 → 브라우저에는 절대 전달하지 않음
- 저장 전에 실제 Gemini API를 한 번 호출해 유효성을 검증한다 (잘못된 키가 저장돼 면접 시작 직전에 실패하는 상황 방지)

**선택하지 않은 대안**
- DB 레벨 암호화(pgcrypto): DB 관리자 권한만 있으면 복호화 가능 → 불충분

## 분석 상태 추적 — `normalize_status` 3-상태 (2026-05-17)

**선택 이유**
- 업로드 응답에서 정제 작업을 분리한 뒤, 각 문서의 진행 상태를 사용자가 명시적으로 알 수 있어야 함

**선택하지 않은 대안**
- 별도 작업 큐 테이블: MVP에 과한 복잡도. v2에서 자동 재시도 도입 시 검토
- 단순 참/거짓 컬럼: 실패 상태를 구분 못해 재시도 UX가 어색해짐

## 에러 처리 철학 — 폴백 없음

**원칙**
> "불완전한 면접 경험은 실전 대응에 치명적이다."

절반짜리 질문 세트로 면접을 진행하면 오히려 잘못된 연습이 된다. AI 호출이 실패하면 즉시 오류를 보여주고 재시도를 유도한다.

**예외 세 곳**
1. **TTS** — 음성이 실패해도 텍스트로 면접을 계속할 수 있다
2. **문서 정제** — 원본 텍스트로 진행하는 폴백은 **의도적으로 쓰지 않는다.** 정제 안 된 PDF 추출본은 양식이 깨져 있어 분석 품질이 떨어지므로, 시작 가드에서 완료를 보장하고 실패하면 명시적 에러를 낸다
3. **평가 일부 실패** — 질문 하나의 평가가 실패해도 리포트 전체를 버리지 않는다. 해당 답변만 실패로 표시하고 나머지는 살린다. **부분 리포트가 무(無) 리포트보다 낫다**

## 평가 결정성 — 질문별 병렬 호출 + 서버 계산

**선택 이유**
- 모든 질문을 한 번에 평가 요청하면 AI가 특정 질문을 조용히 빠뜨리는 일이 있었다. 질문별로 따로 요청하면 누락 자체가 구조적으로 불가능하다
- 동시에 4개까지만 요청해 API 제한을 넘지 않게 했다

**결정 포인트**
- **점수 평균과 총점을 서버가 직접 계산한다.** AI에게 맡기면 같은 답변에도 1~3점씩 다르게 나오는 흔들림이 있었다
- 힌트를 쓴 답변의 점수 상한(30점)도 서버가 무조건 적용한다. 프롬프트로 지시해도 AI가 무시하는 경우가 있어서다
- 검증은 외부 라이브러리 없이 직접 작성한 타입 검사로 처리했다 (초기 설계는 Zod를 쓰려 했으나 실제로는 의존성 추가 없이 해결)

**타임아웃을 예산으로 관리하는 이유**
- 호출 하나하나에만 시간 제한을 두면, 질문이 많고 재시도가 겹칠 때 총 소요가 함수 한도를 넘어 **리포트를 저장하기 직전에 죽는다.** 그러면 평가 결과가 통째로 사라진다
- 그래서 전체 예산(240초)을 두고, 예산이 떨어지면 남은 질문은 재시도 없이 실패로 처리한 뒤 리포트를 저장한다
