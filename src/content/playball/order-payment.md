# 1. 문서 개요
---
### 1.1 목적
- 사용자가 **Hold로 확보한 좌석**을 기반으로 **주문서 생성 → 결제 수단 선택 → 결제(또는 입금 안내) 완료**까지 진행할 수 있는 기능을 정의한다.
- 트래픽 폭주 상황에서 **중복 주문/중복 결제/매크로 시도**로 인한 장애와 재고 왜곡을 방지하기 위해, **주문 생성·결제 요청의 멱등성(idempotency)·세션 바인딩·단계별 검증**을 포함한다.
### 1.2 In scope
- Hold 성공 후 **주문서 화면(티켓 선택 + 예매자 확인)**
- 주문서에서 **권종(성인/청소년/어린이/우대 등) 매수 분해 및 금액 재계산**
- 주문서에서 **다음 단계 클릭 시 주문 생성(orderId 발급)**
- **결제 화면(결제 수단 선택/현금영수증/약관 동의/결제 요청/무통장 입금 안내)**
- 결제 전/중 **Hold·주문 유효성 재검증**, 만료 시 복귀 처리
- 결제 결과(성공/실패/취소) 처리 및 완료 화면(영수증/입금 안내 포함)
    - 화면 내 **취소 기한/취소 수수료 및 자세히보기** 노출
### 1.3 Out of scope
- PG 정산/세금계산서/환불/부분취소/예매 취소 정책 상세
- 쿠폰/프로모션/포인트/복합결제
- 무통장 입금의 실제 은행 연동(가상계좌 발급 등) 세부 구현
### 1.4 용어 정의
- 주문서(Order Draft): 결제 직전 단계의 주문 정보(좌석/매수/권종/금액/예매자 정보)를 확정하는 화면
- 주문(Order): 결제 시도를 위한 서버 측 주문 엔티티(주문번호 orderId 발급)
- 결제 승인: 간편결제(토스페이/카카오페이)에서 결제 완료로 확정되는 상태
- 입금 대기: 무통장 입금 선택 후 지정 시간 내 입금 완료를 기다리는 상태
- IdempotencyKey: 동일 요청(주문 생성/결제 요청)의 중복 실행을 방지하는 키
# 2. 사용자 시나리오
---
### 2.1 Hold 성공 → 주문서 진입(공통)
1. 사용자가 좌석 선택 화면에서 좌석을 선택하고 예매하기를 클릭한다.
2. 서버에 Hold 요청 후 Hold 성공(holdId, expiresAt)을 반환한다.
3. 앱/웹은 **주문서 화면**으로 이동한다.
4. 사용자는 **권종/매수 분해 및 예매자 정보**를 입력한다.
5. 사용자가 **다음 단계**를 클릭하면 서버가 주문을 생성(orderId 발급)하고 **결제 화면**으로 전환한다.
### 2.2 주문서에서 Hold 만료 발생
1. 사용자가 입력/결제 진행 중 타이머 만료(expiresAt 경과) 상태가 된다.
2. 서버 검증 요청 시 Hold 만료 응답을 반환한다.
3. 만료 안내 모달을 노출한다.
4. 확인 시 좌석 선택 화면으로 복귀한다(추천/맵 모드는 기존 토글 정책에 따라 복원).
### 2.3 간편결제
- 성공 케이스
    1. 사용자가 토스페이 또는 카카오페이를 선택하고 결제를 진행한다.
    2. 결제 승인 성공 시 결제 완료 화면을 노출한다.
- 실패/취소 케이스
    1. 결제 승인 실패 또는 사용자가 결제창에서 취소한다.
    2. 실패/취소 안내를 노출하고, 유효시간이 남아있으면 재시도 가능하게 한다.
    3. 유효시간이 만료되면 좌석 선택 화면으로 복귀한다.
### 2.4 무통장 입금
1. 사용자가 무통장 입금을 선택한다.
2. 주문 상태를 “입금 대기”로 전환하고 입금 안내 정보를 노출한다.
# 3. 기능 명세
---
### 3.1 주문서 화면
- 화면 구성
    - 티켓 선택 영역: 권종 목록, 권종별 수량 조절(-/+)
        - 권종 별 수량의 합 = 추천좌석 설정 인원 or 선택한 포도알 갯수의 합
        - 권종 수량의 총합 = 수량 합계가 될 떄 + 버튼을 비활성화 한다.
    - 예매자 확인 영역: 이름, 이메일, 연락처, **생년월일**
    - 우측 요약 패널(My 예매 정보): 타이머, 경기 정보, 좌석 리스트, 금액/수수료/할인, **취소 기한/취소 수수료 + 자세히보기**
    - 하단 버튼: Cancel, 다음 단계
- 동작
    1. 화면 진입 시 holdId로 Hold 유효성 및 가격/좌석 정보를 조회한다.
    2. 타이머는 expiresAt 기준으로 카운트다운하며 0이 되면 만료 처리한다.
    3. 예매자 정보는 다음 단계 클릭 시 필수값/형식을 검증한다.
    4. 다음 단계 클릭 시 서버 요청을 통해 주문을 생성하고(orderId 발급) 결제 화면으로 이동한다.
- 입력 검증(최소)
    - 이메일 형식 검증 (***@ _**.**_)
    - 연락처 숫자/길이 검증 (000-0000-0000)
    - 생년월일 형식 검증 (YYYYMMDD)
### 3.2 권종 분해 및 금액 재계산
- 정책
    - 총 매수는 권종별 수량 합계와 반드시 일치해야 한다.
- 동작
    1. 권종 수량이 변경되면 합계를 즉시 검증한다.
    2. 금액(티켓 금액/수수료/할인/총 결제금액)을 즉시 갱신한다.
    3. 권종 수량의 총합 < 구매 수량합계 일 떄 다음 단계 버튼을 비활성화한다.
### 3.3 결제 화면
- 결제 수단
    - 간편결제: 토스페이, 카카오페이
    - 무통장 입금
- 화면 구성
    - 결제 수단 선택 영역(라디오 버튼)
    - **현금영수증/소득공제** 영역: 신청 여부 선택, 휴대폰번호 표시, 변경하기 버튼
    - **약관 동의** 영역(필수 2개): 이용 약관 동의, 취소/취소 수수료 동의
    - 우측 요약 패널(My 예매 정보): 타이머, 좌석/금액/취소정보 표시
    - 하단 버튼: Cancel, 결제 진행(수단별 문구 변경)
- 동작
    1. 결제 화면 진입 시 orderId로 주문 상태를 조회한다.
    2. 주문이 결제 가능 상태가 아니면 안내 후 적절한 화면으로 이동한다(완료/만료/취소).
    3. 필수 약관 동의가 완료되어야 결제 버튼을 활성화한다.
    4. 결제 수단에 따라 결제 버튼 동작을 분기한다.
        - 간편결제: 결제 요청 및 승인 처리
        - 무통장: 입금 안내 노출 및 입금 대기 전환
# 4. 정책
---
### 4.1 Hold/주문 유효성 검증 정책
- Hold 검증은 다음 시점에 수행한다.
    - 주문서 화면 진입 시
    - 다음 단계 클릭(주문 생성 직전)
    - 결제 요청 직전
- 만료 시 안내 후 좌석 선택 화면으로 복귀한다.
### 4.2 결제 수단 정책
- 결제 수단은 간편결제(토스페이/카카오페이), 무통장 입금만 제공한다.
### 4.3 중복 방지 정책
- 주문 생성 및 결제 요청은 idempotencyKey로 멱등 처리한다.
- 결제 성공 확정 후 동일 주문으로 추가 결제 시도는 차단한다.
